### 1.1. Règles métier particulières

En complément des critères d'acceptation du R1, plusieurs décisions ont été retenues pour préciser le comportement du moteur.

- **Vote incertain (`?`) :** lorsqu'au moins un joueur choisit `?`, le résultat n'est pas validé et une discussion est demandée.
- **Pause café collective :** lorsque tous les joueurs choisissent la carte Café, la partie est mise en pause. Aucune estimation n'est validée.
- **Café joué par un seul joueur :** lorsqu'un seul joueur choisit Café, le vote doit être repris. L'action renvoyée est `reprendre`.
- **Liste de votes vide :** aucun résultat n'est validé lorsqu'aucun joueur n'a voté. Le moteur renvoie l'action `revote`. Ce cas n'est pas couvert par un test automatisé.
- **Médiane avec un nombre pair de votes :** après avoir trié les valeurs dans l'ordre croissant, le moteur retient la valeur centrale inférieure.

### 1.2. Valeurs possibles de l'action

| Action | Signification |
|:---|:---|
| `revote` | Demander un nouveau tour de vote. |
| `pause` | Mettre la partie en pause. |
| `reprendre` | Reprendre le vote lorsqu'un seul joueur choisit Café. |
| `discussion` | Demander une discussion entre les joueurs en cas d'incertitude. |
| `valide` | Indiquer que l'estimation est validée. |

## 2. Démarche TDD (Test-Driven Development)

La méthode TDD consiste à écrire des tests pour définir le comportement attendu, puis à développer le code nécessaire pour les faire réussir.

### 2.1. Suite de tests unitaires

Les tests unitaires sont regroupés dans le fichier `tests/test_regles.py`.

La suite contient **sept tests automatisés** :

1. `test_CA_04_1_regle_stricte` : vérifie que des votes différents ne permettent pas de valider une estimation en règle stricte.
2. `test_CA_04_2_unanimite_premier_tour` : vérifie que l'unanimité est obligatoire au premier tour, même avec la règle médiane.
3. `test_CA_04_3_mediane_nb_impair` : vérifie le calcul de la médiane avec un nombre impair de votes.
4. `test_CA_04_4_mediane_nb_pair` : vérifie que la valeur centrale inférieure est retenue avec un nombre pair de votes.
5. `test_CA_06_1_pause_cafe` : vérifie que la partie est mise en pause lorsque tous les joueurs choisissent Café.
6. `test_CA_04_5_vote_avec_incertitude` : vérifie qu'un vote incertain (`?`) empêche la validation et déclenche une discussion.
7. `test_CA_04_6_unanimite_regle_stricte` : vérifie que l'unanimité permet de valider les votes en règle stricte.

### 2.2. Cycle d'exécution TDD

**Phase Rouge :**

**Phase Rouge :**

Dans une démarche TDD classique, les tests sont écrits avant l'implémentation du code et échouent initialement.

Cependant, l'historique Git du projet ne montre pas cette chronologie : le moteur de règles apparaît avant les tests. Nous ne pouvons donc pas présenter un commit historique comme une phase rouge réalisée avant le développement.

Pour illustrer cette phase, nous avons effectué une démonstration isolée dans le dossier `demo_tdd/`, en utilisant une ancienne version du moteur et un test portant sur le calcul de la médiane. Le test a échoué comme attendu.

Cette démonstration permet d'illustrer la phase rouge, mais ne constitue pas un commit rouge historique du projet.

**Phase Verte :**

La fonction `verifier_tour` a été implémentée dans `src/core/rules.py`. Elle prend en paramètres :

- `votes` : la liste des cartes choisies par les joueurs ;
- `tour` : le numéro du tour de vote ;
- `regle` : la règle de validation sélectionnée.

Elle retourne un dictionnaire indiquant si le vote est validé, la valeur retenue et l'action à effectuer.

Commande utilisée pour exécuter les tests :

```bash
python -m pytest tests/test_regles.py -v
```

Les sept tests automatisés ont été exécutés avec succès à l'aide de pytest. Le résultat a également été confirmé par l'exécution du workflow GitHub Actions.

## 3. Architecture du moteur de règles

La logique métier est séparée des éléments d'affichage et d'interaction. Cette organisation permet de tester les règles indépendamment de l'interface utilisateur.

### 3.1. Organisation des fichiers

```text
capi-planning-poker/
├── src/
│   └── core/
│       ├── __init__.py
│       ├── cards.py
│       ├── game.py
│       ├── models.py
│       └── rules.py
├── tests/
│   └── test_regles.py
├── requirements.txt
└── .github/
    └── workflows/
        └── ci.yml
```

### 3.2. Rôle des composants

- **`src/core/rules.py` :** contient la logique métier du moteur de règles, notamment la fonction `verifier_tour(votes, tour, regle)`.
- **`tests/test_regles.py` :** regroupe les tests unitaires qui vérifient les comportements du moteur de règles.
- **`src/core/game.py` :** contient la logique de gestion de la partie.
- **`src/core/models.py` :** regroupe les modèles de données du projet.
- **`src/core/cards.py` :** regroupe les éléments liés aux cartes utilisées dans le Planning Poker.

Cette séparation permet de tester la logique métier sans avoir besoin de lancer l'interface utilisateur.
